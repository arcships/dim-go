# 界面设计对齐：原则与参数

Status: draft（第三版，按本轮用户反馈逐条核对）
Owner: U1 界面需求与信息架构（前两版由组织侧起草，本版起归 U1 维护）
作用: 把用户的设计判断记成可推导、可判定的依据，供 B2 概念方案与 C1 信息架构引用。
边界: 只记原则、参数与结论；不写视觉规范（归 C2）、不写交互规格（归 C3）、不写概念方案（归 B2）。

## 0 来源规则

每条结论只有两种来源，必须标出来源：

- **原话**：用户逐字说过的判断，引用不改写。
- **推导**：由某条原则或参数推出，写明由谁推出。

推导不得覆盖原话；两者冲突时以原话为准，冲突本身要记进 §7。原则表里的"判定方式"全部是推导，用来让原则可验收；它不得反过来限制原话。

## 1 原则

| # | 原则 | 原话（逐字） | 判定方式（推导） |
|---|---|---|---|
| P1 | 状态即元素变化 | 「状态和ui相关，不是指示器或者大段文字。状态的信息表达应该尽量用ui变化来表达，而不是文字或者专门搞个状态提示器。」「所有的状态都应该是和原始ui元素进行结合做设计，而且不是一个状态一个元素，而是考虑交互和感受上用户需要在哪个ui上看到状态变化。」 | 每个状态必须指到两项：一个**已有元素**，以及该元素**变化的属性**。禁止三件事：新增专用状态容器；一状态一元素；用大段文字承担"状态是什么"。状态相关的文字只补充事实（对象、原因、数值），不承担状态本身。要求指出状态时必须先回答"用户此刻的眼睛落在哪个既有元素上"，答不出即设计未定 |
| P2 | 弹窗只用于阻塞 | 「只有二次确认等block场景才需要弹窗。」 | 出现模态必须能说出"用户不回答就无法继续"的理由。凡可内联、可延迟、可后台完成的交互，不得占用模态。审批是否内联不属于本条原话，是"打扰容忍=低"的推导 |
| P3 | 三区分层 | 「主要操作区和附属信息区域，子操作区域要分层级。」 | 任一屏能指出主操作区、附属信息区、子操作区三者的边界与各自承载；三类内容同层（同一视觉等级或同一容器）即视为未定。读法：原话按"三区并列、彼此分层"采用 |
| P4 | 键盘尽量做，鼠标不能牺牲 | 「尽量做到键盘操作。有很多场景还是需要鼠标。而且不能牺牲使用鼠标的体验。」 | 常用任务有键位路径，但不要求全键盘可达；为键盘做的任何取舍都不得降低鼠标的精度、速度与可发现性；依赖鼠标的场景保留完整鼠标路径。键位覆盖范围与具体键位归 C3 |
| P5 | 信息要包装 | 「展示信息怎么包装，怎么友好，怎么分层，应该要详细设计，而不是把裸的code或者原因丢给用户。」 | 面向用户的信息（尤其错误与原因）不得以裸 code、裸原因出现，须经包装与分层（结论、影响、可展开细节）。本条只要求包装与分层，不要求"给一个动作"；任何动作须先过 P8 与 §6 的第三闸 |
| P6 | 状态不说谎，过程不紧张 | 「状态是不能说谎的，但是我们很多行为要包装的状态更流畅，比如默认重试过程，信息应该没有那么紧张。」 | 每个显示态能指到一条服务端事实或已登记的本地状态；"平滑"只作用于呈现节奏与措辞，不改变事实本身；默认（客户端内部）重试过程不呈现为告警或紧张态 |
| P7 | 可见性克制 | 「有的功能不是都需要在界面上展示出来，就算要展示也不用一次性展示，要考虑交互元素和用户视觉需求。」 | 每个元素过两问：交互上用户此刻是否需要它；视觉上它是否值得占据注意力。答不出的隐藏或按需展开；同一功能的入口不在默认视图一次全展开 |
| P8 | 不虚构 | 「没有的功能不要虚构，不要虚造，ui设计没有顺手的事情，也没有别人都是这么做，所以应该这么做的逻辑。」 | 每个元素能指到一条需求条目或一个真实能力。不画不存在能力的入口，不画假状态，不做"顺手加一个"；设计理由里不得出现"常见做法""别家都这样" |

## 5 状态表达规则（P1 的落地办法）

状态不单独占位，附着在既有元素上。每次表达状态走三步：

1. **在哪感知**：用户在这个状态下，眼睛应该落在哪个已有元素上。
2. **改哪个属性**：标记（打叉、小点）、灰度、描边、形态、位移、可操作性。
3. **一致性**：同一含义在不同元素上是否同一种表达；同一状态是否影响多个元素而非新增一个元素。

示例（均为 P1 的应用，具体落点由 C1 定）：

- 工具调用失败：该工具调用行内某个已有元素变化（如状态标记变叉、整行转次要灰度）。不新增提示条，不弹窗，不出现重试入口。
- 连接中断：受影响的既有区域（如历史区与输入区）自身呈现不可继续，而不是另起一个连接指示层。
- 会话正在运行：既有元素（提交位、流式位置、侧栏行）自身变化，而不是新增运行胶囊。

约束：

- 一个状态可以影响多个既有元素，但不得为此新增容器；同一含义只允许一种主表达。
- 状态表达只反映事实，不得凭空造出可执行动作。动作只有同时满足三条才允许出现：协议里存在对应方法；对应一条写意图（D3 登记）；由用户主动触发。
- 客户端内部重试（D1 的连接层策略）不是用户动作，不得表现为入口。失败按写登记口径分开处理：结果未知先核对（D3），核对确认"没有这次写入"后才允许用新的幂等键重提，核对到上限进入需人工确认、不自动重发；工具调用本身没有重试能力，不得为它画重试入口。依据：用户原话「这种东西没有能力重试的啊」；`docs/domains/D3-write.md`（一次发送、不自动重发、核对后可用新幂等键重提）；`docs/domains/D5-interaction.md`（明确失败允许以新幂等键重试）。

## 6 可见性判定（P7 与 P8 的落地办法）

每个候选元素先过三道闸，任何一道不过就不进界面：

1. **有任务吗**：是否服务于用户此刻要完成的事。答不出，隐藏。
2. **有需要感知的变化吗**：是否要求用户做决定，或必须让用户察觉某个变化。答不出，隐藏或并入已有元素。
3. **有真实能力吗**：是否对应协议里存在的方法与一条写意图。答不出，删掉，不画占位。

过闸后再答两问：**为什么是现在**（为什么必须默认可见，而不是按需出现）；**为什么是这样**（为什么用这个形态，而不是更省的做法）。答案里不允许出现"常见做法如此""别家都这样"。

记录方式：每个界面元素在设计稿旁标一条来源（需求条目、能力方法或状态规则）。没有来源的元素视为虚构，评审直接退回。
