## 2. 项目定位

DimAgent 的 Go 桌面客户端：Go + mygo native UI 承载宿主与界面，Rust `dim-app-server` 通过 protocol v3 提供 agent 能力与全部事实。

三条承诺：

1. **形态**：单一 Go 进程，主界面由 native view 组成，宿主能力取自 mygo。
2. **事实**：session、branch、timeline、approval、model、permission 全部来自 App Server；Go 侧只保留可丢的界面状态与登记的本地状态。
3. **行为**：功能与现役 DimAgent 类似；每项能力按情况判断搬运、保留还是重新实现，判断结果记入需求基线。

阶段作用：先是同一 App Server 的并行客户端，行为对齐后替换 Electron 客户端。

## 3. 范围承诺

### 3.1 承诺交付（main → Go）

连接与 daemon 生命周期；会话投影；会话目录与生命周期；交互与审批；管理面；账号；工作区与文件；附件；终端；宿主外壳。

### 3.3 不在当前范围的能力

以下能力不在当前范围：界面、宿主外观、发布与更新渠道之外的产品化内容，以及：浏览器预览与元素检查、MCP Apps 与 UI 扩展、Chrome 宿主、宠物、CUA、Web Translate、插件市场、本地 sandbox。裁剪记录与理由由 R 记入需求基线；需要时另行立项，不预设阶段。

## 5. 结果包契约

每个领域提交结果包时必须回答五项：

```text
领域：<ID + 名称>
输入：<需要的 owner 方法/通知、代码来源、fixtures、上游接口>
产物：<Go 包与文件职责、领域文档、测试、验收脚本>
验收：<可执行命令 + 可观察结果 + 证据类型>
依赖：<依赖的领域与接口；需要对方冻结什么>
上下文需求：<需要谁提供什么；不确定项与备选>
```

评审标准三条，组织 agent 只按这三条判断：

1. 能否得到预期结果。
2. 是否有缺漏。
3. 是否可验收。

证据规则：

- 验收必须是可执行命令加可观察结果；没有证据的完成不计数。
- 缺真实 App Server、真实仓库、真实账号或目标平台时标 blocked，写明卡在哪个依赖、由谁解除。
- 裁剪判断（搬/留/实现）逐条挂到需求条目，并附理由。

### 5.1 R 结果包要求（需求侧由用户验证）

本要求由组织 agent 给出，产物由 R 领域提交，验收结论由用户给出。

**输入**

- 定位与边界（本文件 §2–§3）
- 产品基线：`dim-electron/docs/architecture/app-server.md`、`dim-electron/docs/acceptance/*`、`AGENTS.md` 的不可违反约束
- main 盘点（附录 A）
- 协议方法与通知清单（以 wire 类型为准）

**产物必须包含六部分**

1. 条目字段定义：需求陈述、来源、裁剪、验收、承接领域、依赖、状态、决策编号；每项附一个反例。
2. 需求条目表：每条写清来源（文件/验收文档/协议方法）、裁剪判断（搬/留/做 + 一句理由）、验收（操作步骤 + 观察结果，或命令 + 输出）、承接领域、状态。
3. 决策项表：每条含选项、影响面、建议与理由、否决后果。决策项必须能在不追问的情况下二选一或多选一。
4. 证据类型与判定口径：fixture、fake App Server、真实 daemon、真实仓库、真实账号、手工，各自的判定标准。
5. 追溯映射：需求 ↔ 承接领域 ↔ 架构组成。
6. 变更记录：日期、变更、原因、影响。

**用户判定什么**

- 每条需求：批准、改口径、移出本阶段。
- 每个决策项：在给定选项里选一个，或新增一个选项。
- 需求整体：是否覆盖十个产品领域、是否与定位一致。

**退回条件（任一命中即退回，不在评审里逐条讨论）**

- 验收写成「符合预期」「正常工作」这类不可观察表述。
- 决策项没有选项，或缺否决后果。
- 需求没有来源，或没有承接领域。
- 十个产品领域有缺项。
- 追溯映射无法落到架构组成。

**组织 agent 评审什么**

能否得到预期结果、是否有缺漏、是否可验收；评审意见以「需补哪一条」的形式给出，不改写领域内容。

**开工包**

### 5.2 R 的颗粒度

判定单位：一条需求 = 一个可独立验收的行为，且只挂一个承接领域。

切分规则：

1. 按可观察能力切，不按控件、协议方法、源文件切。
2. 一条只写一个行为；出现「并且／以及／同时」就拆分。
3. 用户不可见的内部步骤（帧解析、状态装载、重试）并入承载它的需求，写成验收步骤，不单独编号。
4. 同一行为的不同证据阶段（fixture → 真实 daemon）算一条，在验收里分段写。
5. 约束（事实归属、无第二事实、native view）不进入需求编号，单列「约束」小节，由架构与领域落实。

三层：

| 层 | 内容 | 是否编号 | 数量 |
|---|---|---|---|
| L1 能力 | D1–D10 覆盖表，一句话边界 | 否 | 每领域 1 行 |
| L2 行为 | 需求条目，可验收 | 是 | 一个决定一条，不设条数指标 |
| L3 细节 | 验收步骤里的具体操作 | 否 | 随条目 |

数量判定：单领域超过 8 条说明切得过细，合并或下沉为验收步骤；少于 3 条说明覆盖不足。

反例：

- 太细「点击登录后按钮显示加载态」→ 并入登录流程的验收步骤。
- 太粗「支持会话管理」→ 拆为目录、创建、打开、重命名、删除、归档、导出。
- 混合「读取会话并渲染 Markdown」→ 归入打开会话，渲染作为验收观察点。

### 5.3 R 的产物内容与合格判定

`docs/domains/R.md` 十章：

1. 头部：Status、Owner、验证人、范围、依据
2. 字段定义与反例、状态机
3. 覆盖表：D1–D10 边界、来源文档、需求条数
4. 需求条目，按领域分组
5. 约束：不进需求编号，标明由架构与领域落实
6. 决策项：编号、决策、选项、影响面、建议与理由、否决后果
7. 证据类型与判定口径
8. 追溯映射：需求 → 承接领域 → 架构组成
9. 变更记录
10. 未决问题

不写入这份产物：协议方法表（引用 wire）、实现方案与包结构、UI 视觉规格、排期。

合格判定，任一不满足即退回：

- 需求四要素齐全：来源、行为、证据、承接领域
- 没有不可观察的验收表述
- 每个决策项都能二选一
- 一个决定一条；完备性只看能力对照是否全有结论
- 追溯映射覆盖率 100%

### 9.5 状态标准（C2/C3 的固定产物格式）

状态分三层，各层产物与所属阶段不同，不得混写。

**第一层 视觉态（token 层，归 C2）**

控件能呈现的原子视觉态：默认、悬停、聚焦、按下、禁用、选中、加载、错误。每态对应一组 token（前景/背景/描边/不透明度/图标/光标），全局定义一次。需求只写“该控件需支持哪些视觉态”，不写色值与尺寸。

**第二层 语义态映射（归 C2 与 C3）**

业务含义落到视觉上，用全局映射表表达，格式为：语义态 | 视觉态组合 | 判定来源。

规定：语义态优先于视觉态——禁用态吸收悬停与聚焦，不得因悬停把不可用控件点亮。

**第三层 跨组件联动（归 C3）**

分三类，分开写：

| 类型 | 写法 |
|---|---|
| 数据联动 | 触发事实 → 影响集（组件 + 属性：可见·可用·文案·焦点） |
| 上下文联动 | 模式切换（如 tab 切换）→ 可用控件集合、快捷键集合、焦点去向 |
| 输入联动 | 输入条件 → 目标组件可用性与文案 |

每条联动四段：触发条件 / 影响集 / 优先级 / 恢复条件。

**优先级**

多语义态同时成立时按固定优先级裁决，例：待你决定 > 结果未知 > 失败 > 进行中 > 可用。高优先级决定可操作性与主视觉，低优先级只作次要提示；冲突必须能回答为何显示这一个。

**判定颗粒度**

一条状态需求合格需同时满足：判定来源明确、能说出压过谁与被谁压、有恢复条件、能用走查或断言验证。四缺一即退回。

### 9.6 考古必须覆盖状态与联动

A1 除布局与控件外，必须提取：

1. 关键控件的视觉态清单（旧界面实际支持的），标注证据级别。
2. 旧界面的语义态映射（例如“灰掉”在旧界面代表什么），以及映射不一致之处。
3. 跨组件联动清单：切 tab 后哪些控件可用性变化、输入与提交如何互锁、审批出现时输入区与发送键如何变化；每条给触发与影响集。
4. 冲突处理观察：多条件同时成立时旧界面显示哪一个。
5. 转场观察：哪些状态变化有动画、时长来源；取不到就标“未提取”。
6. 缺口：旧界面没有处理的状态（如结果未知、断线），单列为新设计必须补的项。

### 9.7 界面证据的评审覆盖清单

界面证据不同于代码扫描，容易被忽略的是低频状态与边角路径。评审按下列维度逐项打钩，缺项即退回或补交：

| 维度 | 要检查的 | 常见遗漏 |
|---|---|---|
| 入口覆盖 | 每个页面/视图是否有入口与出口，路由清单是否与页面清点一致 | 只在特定状态可达的页面（弹窗式会话、登录引导） |
| 状态覆盖 | 每个控件的语义态是否齐：可用、不可用、进行中、待决、失败、结果未知 | 结果未知、断线、并发提交 |
| 时间维度 | 首次加载、空态、长时运行、跨天、重连恢复 | 骨架屏与加载中、超过一天的活动条 |
| 尺寸与设备 | 三档宽度、窗口最小尺寸、多窗口、缩放与高 DPI | compact 下抽屉与替换式的差异 |
| 输入方式 | 键盘、鼠标、触控板、输入法、粘贴、拖放、辅助功能 | 中文输入法组词、粘贴转附件 |
| 内容极端 | 超长消息、超大代码块、海量列表、大附件、图片 | 虚拟化与文本选择的冲突 |
| 并发与竞争 | 同时提交、审批与提交交错、多会话并行 | 运行中再提交、审批未答时切会话 |
| 失败与权限 | 无权限、服务不可用、超时、账号过期、能力缺失 | 服务端未注册方法时的界面表现 |
| 一致性与文案 | 同一动作不同入口的措辞、图标语义、空态语气 | 两处叫法不一致 |
| 可访问性 | 焦点顺序、全键盘可达、对比度、减少动效 | 只看鼠标路径 |
| 平台差异 | 修饰键、菜单、窗口装饰、字体渲染 | 依赖系统默认快捷键 |
| 恢复与持久化 | 草稿保留、崩溃后状态、未发送内容 | 重启后草稿丢失 |

评审方法：

1. **抽样反查**：从来源仓库抽 3 处与证据对照，确认结论不是转述而是读过。
2. **空单元格检查**：把“对象 × 状态 × 位置”列成矩阵，空格必须有解释（不适用/旧界面未实现/范围外）。
3. **入口可达性**：页面清单里的每一页，必须能说出从哪进、怎么出。
4. **缺口单列**：旧界面没处理的状态必须单列成新设计待补项，不能混在“已覆盖”里。

### 9.10 线框的颗粒度标准

| 层 | 必须画到 |
|---|---|
| 区域 | 每块的名字、尺寸（px）、是否可折叠、滚动范围 |
| 行/单元 | 列表与对话里的重复单元是什么、一行承载哪些字段、行高 |
| 控件 | 每个按钮/输入/选择的文字、可用条件、快捷键、点击后发生什么（对到方法） |
| 文本 | 真实文案（不是占位符），包括空态、错误、等待中的说法 |
| 状态 | 该屏涉及的每个状态落在哪个元素的哪个属性上 |
| 关系 | 元素与数据对象的对应（这一段是什么对象的哪一部分） |

缺任一层即退回；只有方框没有内容的线框不算交付。

### 9.11 对象与关系必须先于线框

画线框前必须先交“界面对象模型”，回答：

1. 有哪些可展现对象（会话、分支、轮次、消息、工具调用、审批、提问、队列项、目标、附件、账号等），各自是什么。
2. 层级关系：谁属于谁（会话 > 分支 > 轮次 > 消息 > 块/工具调用）。
3. 附属关系：右栏内容属于谁；审批与提问属于哪一轮；队列项属于哪一层。
4. 跨对象引用：工具调用引用文件路径、审批引用命令、目标引用轮次等。
5. 界面用词：每个对象在界面里叫什么（术语表）。
6. 展示位置：每个对象在哪一层界面出现（主区行内、输入区、右栏、标题行），以及为什么在这一层。

### 9.12 C0 信息设计（布局之前）

在信息架构（C1）之前增加一层：把界面上可能出现的信息**穷举**出来，形成可判断的清单，再据此分组。没有这张清单，布局只能凭手感。

**必交产物**

1. **信息项全量清单**：来自三处——协议里存在的事实与方法、现役客户端实际展示的内容、用户任务需要但没人展示过的内容（单列为缺口）。
2. **分类**：导航与身份、会话内容、过程与操作、待决事项、设置与上下文、状态、时间与代价、错误与恢复。
3. **每项属性**：来源（哪个方法/事实）、更新频率（每次/每轮/低频）、是否必须一眼可见、与哪些信息必须同屏、现役客户端放在哪、为什么在那儿（证据或反推）。
4. **分组假设**：哪些信息因为“同一时刻被需要”应聚在一起；哪些因为“互斥”应分开；每组给一句理由。
5. **缺口清单**：用户需要但当前无来源、或现役客户端没有的信息，单列并标“需协议/需决策”。

**判定标准**

- 全量性按三源并集判定，分源给覆盖率：
  1. **蒸馏**：现役客户端的信息项、内容形态、本机状态、异常表达（含“原设计可疑”标记）
  2. **对账**：protocol 每个方法 → 产生什么信息 → 落点（方法覆盖率）
  3. **推演**：由六种处境与异常路径推出、前两源都没有的信息
- 合并表每项标来源与裁决（沿用/改造/新增/不展示），裁决要写理由；三源合并不足 100% 即退回。
- 可判断：每项都写了频率与常驻性，不允许“视情况”。
- 可追溯：每项都有来源；无来源的标为缺口，不得混入。
- 分组有理由：每组必须能回答“为什么它们必须在一起”。

C0 未通过不进 C1；C1 的区域划分必须能指回 C0 的分组。

### 9.13 时相与场景（信息设计的第二维）

同一信息在不同时相、不同场景下出现的位置与形态本就不同，不能按“是否重复”一刀切。

**时相**（同一会话内按时间推进）：输入前 → 发送中 → 运行中 → 待决（审批/提问）→ 完成 → 失败/结果不确定 → 回看

**场景**（同一时相下的环境差异）：面板开/合、窗口宽/窄、单会话/多会话、前台/后台、断线/在线

**规则**

1. **同时唯一**：同一时相、同一场景下，同一事实只出现一次。
2. **跨时相有序**：事实可以换位置，但必须写明“什么时候换、从哪换到哪、过渡是什么样”，且不得两个时相同时可见同一事实。
3. **换位要留痕**：从输入区消失的内容，必须在时间线上以对应形态出现（例如草稿变成消息行），不允许凭空消失。
4. **场景切换不得丢失**：窄窗、面板合上时，信息可降级或折叠，但不得丢失；恢复场景后必须回到原位置。

C0 的信息清单必须带“时相 × 场景”矩阵，逐格写信息项；空格要有解释（此相不可见/不适用）。
