# U1 B1 brief：DimAgent MyGo 客户端界面

Status: draft（B1，待组织评审）
Owner: U1 界面需求与信息架构
输入: `docs/project-organization.md` §2–§3、§9.1、§9.3；`docs/ui-alignment.md`（原则与参数）；`docs/domains/U0-design-archaeology.md`（A1 证据）；`docs/domains/U0-framework-baseline.md`（A2 证据）
范围: 只给概念阶段要遵守的定位、用户、边界、参考、原则与成功信号。不画骨架、不选控件、不写视觉与交互规格。

## 1 定位（一句话）

同一个 App Server 之上的第二个桌面客户端：用 native view 承载「看历史 → 提交 → 处理打断」这条日常闭环，先把它做稳，再按批次扩展。

依据：`docs/project-organization.md` §2（形态、事实、行为三条承诺；阶段作用是并行客户端，行为对齐后替换 Electron 客户端）与 §9.3（首批范围）。

这句话同时限定三件事：不与现役客户端抢新功能（行为对齐优先）；界面不生产事实；首批只对一条闭环负责。

## 2 用户与使用状态

### 2.1 用户

**本机上的单个重度使用者**，同时维护多个项目、多个会话，习惯把客户端开着跑长任务。

这是反推结论，不是用户研究结果：依据是现役客户端的结构证据（侧栏项目/会话树、跨会话通知过滤、弹出会话窗），见 `docs/domains/U0-design-archaeology.md` §2.3、§4.10、§4.17。没有访谈与可用性数据；B2 若需要人群差异，只能引用现役客户端的 `office / pro` 双档作为产品事实（同上 §4.16），不得自行发明人群。

### 2.2 使用状态（界面必须成立的六种处境）

| # | 处境 | 用户此刻在问什么 | 依据 |
|---|---|---|---|
| S1 | 等结果、跑长任务 | 还在动吗？跑到哪了？ | §2.2「一眼」层是"最后一条输出 + 是否还在跑"；§7.4 第 1 条（两套客户端都把运行态放在输入位附近） |
| S2 | 被打断（审批/提问） | 要我答什么，答完继续 | §4.1（审批与输入区互斥、同一视线高度）、§7.2（审批替换输入框） |
| S3 | 多会话并行 | 另一条跑到哪了，要不要切过去 | §4.10（通知按是否当前会话过滤）、§4.17（弹出会话窗）、Q-1 |
| S4 | 回看长历史 | 上次改了什么、结论在哪 | §4.7（过程折叠、结果铺开）、§2.2「按需」层；Q-6（100–1000 事件基线） |
| S5 | 出错与不确定 | 这条到底成功没有，我怎么恢复 | §4.11（错误三级、可恢复的常驻）、`docs/domains/D3-write.md`（结果未知先核对） |
| S6 | 长时间驻留（跨天、夜间） | 现在是什么状态，别扰我 | 参数：主题跟随系统、打扰容忍低；§4.14（收起不丢位置） |

这六种处境是首批闭环的验收对象；任一处境下界面无法回答"用户此刻在问什么"，方案即不合格。

## 3 范围与能力边界

### 3.1 首批闭环（`docs/project-organization.md` §9.3）

看历史 + 提交 + 处理审批，含提问这类必须回答的打断。选择理由沿用 §9.3：它同时包含阅读、输入、打断三种基本形态。

### 3.2 后续批次

分支、目标、后台任务、设置与扩展、终端（同上 §9.3）。会话独立开窗（popout）保留余地但排后续（`docs/ui-alignment.md` §4.1 Q-14）。

### 3.3 明确不做（`docs/project-organization.md` §3.3）

浏览器预览与元素检查、MCP Apps 与 UI 扩展、Chrome 宿主、宠物、CUA、Web Translate、插件市场、本地 sandbox。这些是范围外，不进 B2 的任何方案，也不以占位形式出现在首批界面（P7、P8）。未就绪或未接的能力在界面里是隐藏还是可见但禁用，仍未定，见 `docs/ui-alignment.md` §4.2 Q-17 与 §7 C-9。

### 3.4 界面不拥有的东西

- 事实：session、branch、timeline、approval、model、permission 全部来自 App Server（`docs/project-organization.md` §2、`AGENTS.md` §3）。
- 本地：只允许可丢的界面状态与登记的本地状态；清单未定（Q-18）。
- 外部内容：进独立隔离容器，不接入主界面，拿不到 socket 与凭据（`AGENTS.md` §3）。

B2 的任何方案都要能在"事实全来自 App Server、本地状态可丢"这条线上重建，不允许出现"界面自己攒一份历史"。

## 5 设计原则

B2 的每个方案都要逐条打钩；打不上钩的方案不进评审。原则全文与判定方式见 `docs/ui-alignment.md` §1，此处只给对概念方案的约束。

| # | 原则 | 对 B2 的要求 |
|---|---|---|
| P1 | 状态即元素变化 | 方案里每个状态写明"落在哪个已有元素的哪个属性"；不出现状态容器、不出现一状态一元素、不用大段文字承担状态 |
| P2 | 弹窗只用于阻塞 | 方案里出现的每个模态都要能说出"不答就无法继续"；其余打断不得占用模态 |
| P3 | 三区分层 | 每个画面的主操作区、附属信息区、子操作区能指认，且三者不同层 |
| P4 | 键盘尽量做，鼠标不能牺牲 | 方案的关键动作给出键盘与鼠标两条路径，并说明鼠标路径不被削弱 |
| P5 | 信息要包装 | 方案里错误与原因有结论层与细节层；不把裸 code、裸原因交给用户 |
| P6 | 状态不说谎，过程不紧张 | 方案里每个显示态指到事实或登记状态；默认重试过程不以告警语气呈现 |
| P7 | 可见性克制 | 方案说明"哪些功能不出现、哪些不默认出现"；首屏元素逐项过交互需要与视觉负担两问 |
| P8 | 不虚构 | 每个元素带来源（需求条目 / 能力方法 / 状态规则）；不出现顺手加的入口与假状态 |

## 6 成功信号（可判定）

每条给判据与判定者；视觉基线不在 B1（归 C2 与 E 阶段）。

| # | 信号 | 判据 | 判定者与阶段 |
|---|---|---|---|
| G1 | 闭环成立 | 走查五个场景全过：首次进入空态、读一条有历史的会话、提交并在运行中再提交、处理一次审批、断线后恢复。任一场景卡住即不成立 | 用户，E 阶段走查 |
| G2 | 没有虚构 | C1 元素清单里每个元素都能指到需求条目、能力方法或状态规则；无源元素为 0 | 组织评审，C1 门禁（退回条件） |
| G3 | 状态可归因 | C1 状态可见性矩阵中每条状态有判定来源、压过谁、恢复条件；走查时不出现无源状态 | 组织评审 + 用户过目，C1 |
| G4 | 两条输入路径都成立 | 首批闭环的每个动作有键位路径与鼠标路径；鼠标完成同一动作的步数不多于现役客户端；键盘不需要未公开键位 | 走查 + 与 U0 §4 的模式清单对照，E 阶段 |
| G5 | 长会话可用 | 在 100 个与 1000 个事件的会话上，滚动、选择、查找均可用；性能数值由 C4 定预算，B1 只判"可用" | 走查，E 阶段（依赖 C4 预算） |
| G6 | 行为对齐可追溯 | 首批范围内每条需求在现役客户端有对照，差异逐条记入 R 的裁剪判断 | 组织评审，对照 R 的追溯表 |

不成立的常见样子（评审时按此识别）：靠新增一条状态条解释状态；把"下一步"写成不存在的按钮；首屏一次铺开全部功能；键盘路径要靠用户记住隐藏键位；用"常见做法"解释形态。
